작성 2026-08-31 · 레포 `nine_press` · 챗 세션에서 넘김

## §0 이 문서의 성격

**구현 프롬프트가 아니다. 코드를 고치지 마라.**

챗 세션에서 「원고 입력층」을 어떻게 세울지 논의했다. 그 **이유와 방법**을 적었다.
레포를 손에 쥔 쪽에서 **현실적인 문제와 더 나은 대안**을 달라.

```
이 턴에 하는 것    읽기 · 실측 · 판정 · 대안 제시
이 턴에 안 하는 것  코드 수정 · 커밋 · 파일 생성
```

**사용자 결정은 이미 끝났다. 되묻지 마라.** §4 에 박아 뒀다.
묻는 것은 §6 에 있고 · **전부 기술 판단이다.**

**미리 밝힌다.** 챗 세션은 프로젝트에 붙은 프롬프트 문서 다섯(N1 · N1-b · N1-c · N2 둘)만
보고 설계를 시작했다. 레포를 읽고 보니 절반이 이미 지어져 있었다 —
배열 모델 · 넘침 검사 · 요소 어휘 역산 · 예산표 · 용어 정리.
**아래에도 같은 중복이 남아 있을 수 있다. 발견하면 그것부터 지적해 달라.**

## §1 왜 지금 이것인가

### 1-1 사용자의 말

> 기능적으로는 다 정리가 되어 가고 있어. 이제 실제 이 앱의 최대 기능에 대한 내용의 구조를 짜야 해.
> 마크다운 파일을 클로드에게 줄 때 이 편집기의 형식을 전제로 깔고 · 그 형식에 맞게 원고를 작성해 달라고
> 해서 마크다운으로 받고 · 그걸 편집기에 집어넣는 형식으로 하려는 거야.

`HANDOFF.md` §6 이 「계획의 마지막 기능이 닫혔다」고 적은 그 지점이다.
사용자가 가리킨 것은 설계 §6 의 **T1 · T2 · T3** 이고 · 설계 §11 이 「이 앱의 본론」이라 부른 것이다.

### 1-2 지금 비어 있는 자리

```
원고 → [ ??? ] → 페이지 JSON → 렌더러 → 지면
```

렌더러는 정수 좌표까지 정확하고 편집기는 계층 · 크기 · 굵게 · 요소 순서까지 만진다.
그런데 **문안을 만드는 길이 손으로 JSON 을 쓰는 것뿐이다.** 설계 §1 이 「JSON 을 손으로 고치는
것은 「쉽게」가 아니다」라고 못박은 그 상태다.

### 1-3 순서 · **여기가 첫 번째 이견이다**

**두 정본이 어긋나 있다.**

```
HANDOFF.md §6      다음 착수점 = 「② 얹는 층」   (선 얹기 · 도형 배경 이미지 · 박스 밖 도형)
설계 v2 §6          다음 = T1 원고 규격서
```

**챗 세션 판단은 T1 이 먼저다. 근거 셋.**

| | 근거 |
|---|---|
| ① | `HANDOFF.md` §6 이 스스로 얹는 층을 미룬다 · 「비움으로 넘기는 길이 이미 있다 · N-이관 39쪽에서 세어 보고 판정해도 된다」 |
| ② | 설계 §6-1 이 T1 착수 조건을 「격자 규격만 서면 된다」로 걸어 놨고 · N-기준선 · N-배경 · N-글자 가 다 닫혔다 |
| ③ | **T 계열이 N-이관의 도구다** · T1 · T3 없이 39쪽을 옮기면 표 50건을 손으로 JSON 으로 짠 다음에 변환기를 만들게 된다 |

③이 제일 크다. 순서를 뒤집으면 같은 일을 두 번 한다.
반대로 T 계열을 먼저 세우면 **N-이관이 변환기의 첫 실전 시험**이 되고 · 그 39쪽을 옮겨 보면
얹는 층이 정말 필요한지도 같이 판정된다.

**이 판단이 틀렸다면 코드 근거를 대고 반박해 달라.**

## §2 하려는 것

```
[ T1 규격서 ] + [ 문체 기준집 ] + [ 건별 지시서 ]
        ↓ 클로드가 읽는다
   원고 마크다운 (.md)
        ↓ T3 변환기 · 마크다운 파싱 + 렌더러 계약 검증
   페이지 JSON
        ↓ 편집기에서 사람이 고친다
   렌더러 → HTML → PDF
```

| | 무엇 | 상태 |
|---|---|---|
| **T1** | 원고 규격서 · 문법 · 레이아웃 선택 기준 · 박스별 예산 · 표기 규칙 | 없다 |
| **T2** | 템플릿 · 제안서 1종 | 없다 · **뒤로 미룬다** · §4 |
| **T3** | 변환기 · 마크다운 → 페이지 JSON | 없다 |
| 문체 기준집 | 개조식 · 어미 · 부호 · 금지어 | **앱 밖** · 별도 관리 · 초안 완성 |

## §3 분담 · 클로드와 편집기

설계 §2-2 를 요소 배열 시대에 맞춰 다시 그은 것이다.

| | 클로드 | 편집기 |
|---|---|---|
| 페이지 | 쪽 수 · 순서 · 장 구성 | 번호 부여 |
| 페이지 속성 | 모드(카피·연속) · 레이아웃 | 비율 조정 · 레이아웃 교체 |
| 글 | 페이지 제목 · 요지 · 카피 · 박스 제목 · 요약 · 문단 · 목록 · 표 내용 · 출처 | 없음 |
| 강조 | 어느 말을 굵게 할지 (`**`) | 굵게 버튼 |
| 꼴 | **없음** | 좌표 · 도형 · 색 · 계층 · 크기 · 자간 · 행간 |
| 조판 열쇠 | **없음** | 표 폭 · 표 높이 · 그림 높이 · 안여백 |
| 검사 | 예산 안에서 쓴다 | 박스재기 · 기준선 · 계약 검증 |

**원고가 못 주는 것 셋** · 파서가 오류로 막는다.

```
좌표 · 픽셀 · 색 · hex
도형 속성 (배경 · 모서리 · 테두리 · 그림자 · 투명도 · 반전)
페이지 번호
```

## §4 방법 · 사용자 확정 사항

**전부 확정값이다. 되묻지 마라.**

```
① 문서 종류      제안서 하나만 · 브리프 · 시뮬레이션은 나중
② 표본          content/sokcho/실행계획서.json 18쪽
③ 순서          T1 → T3 → N-이관 → 얹는 층 판정 → T2 → B 보강
④ 문체          앱 밖 · work-rules 스킬 · 고정본 + 건별 덮어쓰기 · 규격서는 「예산이 이런 글을 강제한다」 한 절만
⑤ 왕복          미정 · §6 5 에서 의견을 묻는다
```

**T2 를 뒤로 민 이유** · 템플릿은 39쪽을 실제로 옮겨 봐야 무엇이 반복되는지 보인다.
지금 뽑으면 상상이 섞인다.

### 4-1 예산 계산기 · `scripts/예산.mjs`

**규격서의 예산표를 손으로 쓰면 코드가 바뀌는 순간 거짓말이 된다.**
그리고 그 거짓말을 클로드가 그대로 믿고 원고를 쓴다.

```
입력   레이아웃 G1~G12 × 모드(카피 · 연속)
출력   박스마다 「한 줄 몇 자 · 몇 줄 · 머리가 붙으면 몇 줄」
근거   render/index.js 의 영역() · 확정높이() · 설계 §5-2 의 두 식
```

설계 §5-2 표는 **옛 계층 셋(라벨 · 제목 · 문단) 시대 값**이다. 지금은 요소 열한 가지에 배열이라
조합이 훨씬 많다. 그래서 표를 갱신하는 게 아니라 **뽑는 스크립트**로 간다.

### 4-2 원고 마크다운 표기 · 초안

**요소 열한 가지를 마크다운이 자연스럽게 받는 만큼 받는다.**

```markdown
---
문서명: …
서식: 제안서
---

## 03 · 페이지 제목
레이아웃: G3   모드: 연속

# 메인카피
## 서브디스크립션
요지: …

### 박스
#### 박스 제목
~ 요약 한 줄
본문 문단

- 목록 항목
1. 번호목록 항목

| 헤더 | 헤더 |
|---|---|
| 값 | 값 |

[그림: assets/캡처/x.svg · 높이 6]
[빈칸: 2]
[비움: 3 · 지도는 키노트에서]
출처: …
```

```
###    박스 시작 · 개수가 레이아웃 박스 수와 다르면 던진다
####   박스 제목 (29)      ~   요약 (26)      평문   문단 (24)
표     마크다운 표를 그대로 받는다 · 폭 · 높이 열쇠는 원고가 못 준다
[…]    표기 요소 · 그림 · 빈칸 · 비움
```

**표를 마크다운 표로 받는 것이 이 형식을 고른 큰 이유다.** 실물에 표가 50건인데
클로드가 가장 안정적으로 쓰는 형식이 마크다운 표다.

**JSON 을 클로드에게 직접 뱉게 하지 않는 이유** · 한글 열쇠 · 중첩 배열 · 이스케이프 ·
쉼표 하나로 긴 문서가 깨지고 · 사람이 눈으로 읽고 고칠 수 없다.

### 4-3 수정 왕복 · **단방향에 기울어 있다**

편집기가 이미 계층 갈아타기 · 크기 · 굵게 · 요소 순서 · 도형까지 만진다.
그래서 **초안만 마크다운으로 받고 수정은 편집기에서만** 하는 단방향이 맞을 수 있다.

왕복을 연다면 필요한 것.

```
페이지 식별자   안 변하는 id · 3쪽을 지워도 5쪽이 계속 5쪽이어야 한다
교체 단위      페이지 하나 · 박스 단위는 문맥이 잘리고 문서 전체는 흔들린다
회귀 관문      안 건드린 페이지가 한 글자도 안 바뀌었는지 · N1 §5-1 과 같은 사고
```

## §6 묻는 것 · 아홉

**전부 기술 판단이다. 파일과 줄 번호로 근거를 대라. 실측과 추측을 구분해 적어라.**

### 1 · 순서

`HANDOFF.md` §6(얹는 층)과 설계 §6(T1)이 어긋나 있다. §1-3 근거 셋이 코드 상태에 비추어 맞나.
얹는 층을 먼저 해야 하는 코드 쪽 이유가 있으면 대라.

### 2 · 예산이 정말 뽑히나

`확정높이()` 가 문단 · 목록 · 번호목록에 `null` 을 돌려준다. 가변 높이라서다.
그러면 「이 박스에 문단 몇 줄」을 어떻게 세나.

```
채움류가 하나면    남은 높이 ÷ 42 로 떨어질 것 같다
채움류가 여럿이면   어떻게 나누나 · 표 "채움" 과 문단이 같은 박스에 있으면
```

**§4-1 이 실현 가능한지 · 아니면 다른 계산 경로가 있는지 답해 달라.**

### 3 · 마크다운 표기가 못 가르는 자리

§4-2 초안에서 파서가 못 가를 곳이 어디냐. 특히,

```
제목(####)과 요약(~)의 구분이 이 표기로 충분한가
표의 폭 · 높이 열쇠를 원고가 못 주면 표가 실물처럼 나오나
수치 요소를 어떤 표기로 받나 · 초안에 빠져 있다
비움 · 빈칸의 값(42 블록 수)을 원고가 세는 게 맞나 · 그건 조판 아닌가
```

### 4 · **원고만으로 39쪽이 재현되나** · 제일 중요한 물음

`content/sokcho/실행계획서.json` 18쪽을 실측해서 답해 달라.

```
표 50건 중 폭 · 높이 열쇠를 쓴 것이 몇 건인가
그림 높이 · 안여백 · 요소 도형을 쓴 박스가 몇 개인가
그중 「템플릿이나 편집기가 자동으로 채울 수 있는 것」과 「사람이 그 자리에서 정한 것」의 비율은
```

**조판 열쇠를 쓴 비율이 높으면 §3 분담이 무너진다.** 그러면 원고는 초안까지만 만들고
나머지를 편집기가 받는 구조가 되어야 하고 · T2 템플릿이 앞으로 당겨져야 한다.
**숫자를 보고 판정해 달라.**

### 5 · 왕복이냐 단방향이냐

`roundtrip.mjs` 는 「편집기 제자리 편집이 문안을 깨뜨리는가」 검사다 ·
챗이 말한 「마크다운 ↔ JSON 무손실 왕복」과 다른 물건이다.

```
페이지 JSON → 마크다운 역변환을 얹는 비용이 얼마나 되나
지금 문안에 안 변하는 페이지 식별자가 있나 · 없다면 넣는 비용은
편집기가 이미 강력한데 원고 왕복이 값을 하나
```

### 6 · 변환기 위치

`scripts/` 인가 · `render/` 인가 · `app/api/` 인가.
편집기 import 로 붙이려면 어디에 있어야 하나. `render/` 는 「node 의존 0」 규약이 있는데
마크다운 파서를 넣으면 그게 깨지나.

### 7 · 검증 주체

변환기가 렌더러 계약(박스 개수 · 표 행 길이 · 색 형식 · 크기 계단)을 **다시 구현하면 이중 관리**다.
렌더러를 그대로 불러 던지게 하고 그 오류를 잡아 줄 번호로 옮기는 편이 나은가.
그렇게 하면 오류 메시지에 **원고 줄 번호**를 어떻게 붙이나.

### 8 · 오류 메시지의 수신자

오류를 사람이 읽는 말이 아니라 **클로드에게 그대로 던질 수 있는 말**로 내고 싶다.

```
「03쪽 박스 2 · 문단 예산 18줄 · 실제 24줄 · 6줄 초과」
```

지금 렌더러 · `박스재기.mjs` 오류 형식에서 이 꼴로 가는 비용은.

### 9 · 더 나은 대안

**마크다운이 정말 맞나.** 다른 입력 형식이 나은 경우가 있으면 근거와 함께 대라.
그리고 **§2 그림에서 통째로 빠진 단계**가 있으면 지적해 달라.

## §7 답의 형식

```
①  §6 아홉에 하나씩 답한다 · 번호를 달고 · 파일과 줄 번호를 댄다
②  실측과 추측을 구분해 적는다 · §6 4 는 반드시 실측이다
③  「챗이 이미 있는 걸 다시 만들려 한다」 싶은 것을 먼저 적는다
④  순서(§1-3)와 분담(§3)에 이견이 있으면 근거를 대고 반박한다
⑤  다음 블록을 무엇으로 잡을지 제안한다 · 하나만
```

**코드를 고치지 마라. 커밋하지 마라. 파일을 만들지 마라.**
판정이 오면 챗 세션이 사용자와 결정하고 · 구현 프롬프트를 따로 낸다.
